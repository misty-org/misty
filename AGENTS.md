# UI conventions

- Shared dropdown and context-menu selections use checkmarks, never dot indicators. Collection toolbars must not add a filter menu that duplicates their visible section tabs.
- Use the approved black, white and gray palette. Do not introduce green, sage, colored status dots, tinted selections or accent-colored focus rings unless the user explicitly requests color for that surface. Convey status through text and icons as well as contrast.
- Exception: item-type icon glyphs on content surfaces (the file explorer, and collection rows and cards on Spaces and other collection pages) use the shared tones in `src/shared/ui/icons/itemTones.ts`. Color the glyph only; icon tiles, hover, selection, focus and status stay monochrome. Tones mark what an item is, never its state. The app navbar, all sidebars (including the Extensions rail) and browser chrome stay uncolored. Add new kinds to the shared map rather than picking colors locally.
- Exception: official brand logos for connected apps (Integrations rows and tiles, and the app chips under the Agents composer) and for source browsers in the browser import flow (onboarding, Settings and the Bookmarks page) keep their original artwork via `BrandIcon` from `src/shared/ui/icons/brand-icons`. Never recolor them or hand-draw a substitute; apps without artwork fall back to a monochrome Lucide icon. Status around them stays text and icons.
- Exception: status dots on agent conversation rows (the Agents sidebar Recents) follow Claude's session list: gray at rest, pulsing while working, amber when the run needs the user, red when it failed, using the `--misty-status-*` tokens in `src/styles/App.css`. Every dot keeps a text label (tooltip and screen reader). Do not spread status color to other surfaces.
- Exception: the optional accent color (Settings › Appearance › Accent color, `src/features/settings/store/accentColor.ts`) colors only the active tab marker, switches that are on and text selection, through `--misty-accent`. It is off by default. Its presets are the Spaces avatar pastels plus a custom color. Do not add other accent surfaces or a token-based theme system.
- Never show "Loading…" or "Preparing …" text. First loads render animated skeletons shaped like the content that replaces them (`Skeleton`, `SkeletonList`, `SkeletonDocument`, `CollectionSkeleton` from `@/shared/ui`). Refreshes keep the current content on screen; never blank a surface or drop to a skeleton while revalidating.
- Preserve the existing settings sidebar geometry, Search field and Lucide icons. No group dividers, Account footer, nested disclosures, tab strips or chevrons on settings buttons (sidebar entries and rows alike). Each area opens a cohesive scrolling page with small, muted section headers.
- `src/features/settings/settingsRegistry.tsx` is the single settings navigation registry. Use `DesktopSettingsSection`, `DesktopSettingsRow` and `SettingsControls` for settings UI. Area names must not contain ampersands; each area has a unique icon.
- Settings pages are plain lists: no card boxes, rows separated by hairlines, every control in one fixed right-hand column so edges line up. Reset appears only while a value differs from its default and never moves the control. Up to four short choices use a segmented control; longer lists use a checkmarked dropdown, never a stack of radio buttons. Failures show as an inline notice in plain language, never raw setting keys or server errors.
- Settings changes belong to the account on the server. Do not add Local only modes, device-only overrides, profile pickers or scope badges. Device identity and OS vault secrets are distinct from account preferences; never upload unlock secrets as ordinary settings.
- Approved Sync direction: `docs/design/sync/BRIEF.md`, revision 2, including the approved monochrome palette and server-account settings model. Historical mockup screenshots do not override these instructions.
