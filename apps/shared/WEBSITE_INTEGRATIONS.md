# Planner and Journal website integrations

Journal offers Google Docs, Microsoft Word, Notion, and Microsoft OneNote. Planner offers Google Calendar, Outlook Calendar, Microsoft To Do, Todoist, Trello, Asana, and Jira Cloud. These destinations show each service's website. Misty Notes, Drawings, Tasks, Agenda, and Roadmaps retain their existing data and routes; no import, capture, synchronization, or new agent tooling is introduced.

The `createWebsiteApp` wrapper keeps the native app lifecycle separate from the integration gallery and website workspace. Browser rendering uses the existing shared SDK browser view. Added services and account-specific pins populate the app-owned navigation tree. Each account, pin, service, page, and pane selection has an independent local record. Temporary authentication addresses and native popup handles are never saved as pins or restored pages.

Browser provider IDs and service/authentication domains come from `mistyBrowserProviders` in the public SDK contracts. The host's SDK sync script copies that registry into the native provider policy; parity tests detect drift. Journal and Planner require only the additional `browser.navigate` scope. Their catalog permission versions are incremented so the existing installation review flow applies.

Website accounts require macOS 14 or newer. A host must explicitly advertise a service in `browser.availability.supportedProviders`; older hosts show an update message. The host derives WebKit identities from deployment, Misty account, owning app, provider, and website account. Account removal closes matching views across panes and clears only that named WebKit store, including cookies and local website storage. It leaves remote content and other apps' profiles untouched. A failed cleanup keeps a pending-removal record for retry.

Development continues to use the host's single `.env` and configured `MISTY_APPS_DIRECTORY` (or public alias `VITE_MISTY_APPS_DIRECTORY`). Build locally with `npm run build:apps -- journal planner` from misty-apps. Local component replacement still requires the catalog release and permission contract to match the server-issued grant. Updating a server catalog or publishing packages is a separate release step; no capability grant is widened by this implementation.

Validation includes shared-store and UI tests, native route regression tests, frontend/native registry parity, native backend ownership and popup tests, and a disposable signed-package macOS probe. The native probe is selected with `MISTY_SDK_PROBE_WEBSITE_APPS=1` when running the existing SDK package probe for Journal or Planner against a candidate catalog. Its only website data is a disposable local-storage marker; it does not sign in to third-party services or access real account content.

Authenticated flows remain unverified for all eleven services. In particular, organization-specific SSO redirects may need explicit policy additions after verification. This is not a promise that every third-party login configuration works inside WebKit.

## Shared website chrome

Inbox, Social, Planner, Journal, and Library use `WebsiteHeader`, `PlatformPanel`, and `PlatformDirectory`. Refresh stays on the left. More holds provider actions, profile creation/renaming, pins, sharing, and app selection. An icon-only profile dropdown appears when multiple isolated profiles exist and switches the active profile directly. There are no provider settings pages. Catalog rows open their website; legacy `manage=accounts` links also open the website. Adding a profile uses a compact action dialog, including any required workspace or account-type fields. The app catalog retains its simple app name, one search field, and all available providers.

The More menu in Browser and embedded website apps includes an inline Zoom row matching the neighboring item height, with the label on the left and minus, the current percentage (select to reset to 100%), and plus controls on the right. Zoom affects only website content, ranges from 25% to 500%, and is independent for each live browser view. The menu stays open while adjusting zoom. Controls are disabled until the view is ready and while a change is being applied; a failed change retains the last confirmed percentage. Browser pages allow horizontal overflow, with a persistent bottom scrollbar when content extends beyond the viewport; the surrounding app stays fixed. The scrollbar supports dragging and keyboard navigation and disappears when the overflow is removed. At enlarged zoom, overflowing fixed headers move with horizontal scrolling while retaining their fixed vertical position.

Integrations opens a centered host Dialog with focus containment, Escape/backdrop dismissal, and focus restoration. It uses the existing `drawer=integrations` route for backward compatibility; the wrapper strips that parameter before updating the child. Provider views stay mounted and active at their original size; the host modal layer moves native websites behind the renderer. Profile records, cookies, pins, and API authorization stay unchanged. A profile is not a verified provider identity: multiple website accounts may live inside one isolated profile, and API connections remain separately authorized.

Each host app row retains its disclosure and plus action. Existing gallery and shared-content deep links still work. Inbox is provider-only; old native Inbox links resolve to the website or provider picker. Saved profiles appear in navigation without a sign-in confirmation step.

Inbox and Social pins have independent `provider-page-pin-v1:` records and include their owning website account in the navigation route. As with Planner, Journal, and Library, transient sign-in addresses cannot be pinned. The local build command for all affected apps is `npm run build:apps -- inbox chat planner journal library`.
